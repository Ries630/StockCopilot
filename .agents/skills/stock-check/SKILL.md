# Stock Check — 株式現物の保有分析

## When to Use

ユーザーが保有株の分析、「ストックチェック」「持ち株どうすべき？」「9999 を分析して」を依頼したとき。対象は **現物の株式・ETF (日本株 / 米国株)**。仮想通貨のスイング保有は別スキルの担当で、こちらでは扱わない。

## 大原則

- **このスキルは発注しない。** 分析と提案のみ。執行はユーザーが手動で行う。このリポジトリには発注コードが無く、証券会社の取引 API も追加しない
- **スケジュール実行される前提で書く。** 応答できる相手がいない状態で完結する必要がある。**確認を求めて止まらない** — 前提が不確かなら、質問ではなく「何を前提に置いたか」を出力に明記して進める
- 分析はシリーズもの。**必ず前回ジャーナルとの差分で語る** (単発分析の繰り返しにしない)
- **確定足だけで判定する。** データ取得は必ず `analyze.py` を通す。yfinance を直接叩いたり、他ツールで取った株価を混ぜたりしない
- **信頼度の星は付けない。** 判断は ホールド / 積増し / 部分利確 / 売却 / 保留 の 5 ラベルと根拠で示す。現物のホールド判断は perp より単純で、毎回★を付けると形骸化する。**「保留」はデータ不足で判定が成立しない場合にのみ**使う
- **保有情報をリポジトリに書かない** (下記)

## 取り扱い注意 (public リポジトリ)

このリポジトリは **GitHub で公開されている**。銘柄・株数・口座名・売買判断を書いてよいのは `journal/journal.md` `journal/lessons.md` `config/watchlist.py` だけで、いずれも `.gitignore` 済み (CI でも追跡されていないことを検査している) → `docs/adr/0008-no-holdings-in-repo.md`

- ❌ 上記 3 ファイルをコミットする
- ❌ コミットメッセージ・Issue・PR に銘柄や株数を書く (必要なら「保有銘柄A」に置き換える)
- ❌ `config/universe.py` に保有銘柄を書き足す (`screen.py` が保有を**既定で除外する**ので、書いても母集団には入らない)
- ❌ `analyze.py` の出力をリポジトリ内の追跡対象ファイルに貼る

## ファイル構成

パスはリポジトリルートからの相対。**`pip install` は禁止**、常に `uv run` + PEP 723。

- `analyze.py` — 保有取得 + 日足/週足の指標計算 (STEP 1)
- `docs/output-contract.md` — **出力の読み方の正**。決算注記・保有の鮮度・警告の意味、
  および**実行モードごとの外部参照の可否**はすべてここ
- `docs/report-contract.schema.json` — **中間表現の構造の正**
- `docs/report-contract.md` — **中間表現の意味と判断ラベル定義の正**
- `reports/latest.json` — **前回の中間表現**。シリーズ分析の起点 (STEP 2)
- `journal/journal.md` — 執行の台帳 + 運用メモ (追記専用。無ければ新規作成)
- `journal/README.md` — **執行の書式と、運用メモに何を書くかの正**
- `journal/lessons.md` — 運用教訓 (追跡対象外。無ければ空として扱う)
- `lib/holdings.py` — 保有データの読み取り (このスキルから直接は呼ばない)

保有データの出所は別プロジェクト (Investment) の生成物で、`lib/holdings.py` が read-only で読む。**その生成物を書き換えない。**

## ワークフロー

### STEP 0. 運用教訓の読み込み

`journal/lessons.md` を読む。過去の運用で判明した注意点が入っている (無ければ初回として扱い、以降のステップをそのまま進める)。

### STEP 1. 保有取得 + 指標計算

```bash
uv run analyze.py           # 保有全銘柄
uv run analyze.py 9999 AAPL # 銘柄指定
```

**出力の読み方は `docs/output-contract.md` に従う。** 実行時刻の条件、保有データの鮮度 (`as_of`) と実効保有の定義、決算注記の 7 パターン、警告の意味はすべてそこが正で、この SKILL.md には写経しない。

指標の読み方は **週足 = 上位トレンド、日足 = 執行判断** (crypto の 4H/1D に対応する株式版)。

### STEP 2. 前回の中間表現と執行記録の読み込み

`reports/latest.json` から、銘柄ごとの**前回の結論 (`verdict`)・キーレベル (`levels`)・シナリオ (`scenario` / `prose`)** を把握する。構造は `docs/report-contract.schema.json`、意味は `docs/report-contract.md` を見る。

- **無ければ `journal/journal.md` の最終エントリを読む** (2026-08-20 までのエントリは定型の分析を含む)。それも無ければ初回として扱う
- この fallback は移行期のためのもので、JSON が溜まったら消す → `docs/adr/0025-journal-as-ledger-and-memo.md`

あわせて **`as_of` 以降のすべての `### 執行` を `journal/journal.md` から拾い、実効保有を計算する**。書式は `journal/README.md` の「執行の記録」を見る。**執行の台帳はジャーナルのままで、JSON には移っていない。**

#### 実効保有は提示する。問い返さない

**このスキルはスケジュール実行される。** 応答できる相手がいない前提で成立する必要があるため、**確認を求めて止まってはならない**。「売買はありましたか」と聞かない。

代わりに、計算結果を出力の冒頭に必ず置く。ユーザーが出力を読んだ時点で誤りに気づけるようにするのが目的で、対話ではなく**記録の可視化**で担保する。

```
実効保有 = as_of YYYY-MM-DD + 執行記録 N 件
  9999 XXX株 → YYY株 (MM/DD に -ZZ株 @¥X,XXX)
  他 M 銘柄は変更なし
```

執行記録が 0 件なら「執行記録なし (as_of 時点のまま)」と明記する。**黙って省略しない** — 記録が無いのか、拾い忘れたのかが区別できなくなる。

#### 売買の報告は売買時点。スキル実行はその最終期限

執行の記録はユーザーが売買した時点で行う運用になっている (約定直後が単価・株数ともに最も正確なため)。スキル側から報告を催促しない。

記録漏れがあった場合は、**保有データの `as_of` が次に動いたときに検出する**。新しい保有と「古い `as_of` + 執行記録」を突合し、食い違えばそれが漏れである。低頻度の更新を同期ポイントとして使う。突合した結果はジャーナルに残す。

#### 増減が見つかったら

実効保有と前回の中間表現の株数が食い違う銘柄は、**執行内容を先に特定してから**分析に入る。特定できない食い違いは推測で埋めず、その旨を出力に明記する。

### STEP 3. 分析

1. **週足**でトレンド判定 (EMA20/50/200 の並び、ADX ± DI、MACD ヒストグラム)
2. **日足**で執行判断 (RSI / StochRSI の過熱、BB %B、20 日・60 日高安との距離、OBV の増減)
3. **シナリオ進捗**: 前回の中間表現の `levels` と現値を突き合わせ、成立へ前進 / 停滞 / 否定に接近 (無効化ラインまで何 %) を判定する
4. **決算日**: `analyze.py` が出す決算注記を**トリガーの有効性の問題として扱う** (日程の報告で終わらせない)。読み方と `⚠` の有無による違いは `docs/output-contract.md`。それを踏まえた判断は下の「決算をまたぐ判断」に従う。財務の深掘りが要る場合は別プロジェクト (dexter-jp / 日本株) に回す — このスキルはテクニカル担当
5. **自動運用口座の扱い**: ロボアド等、自動リバランスされる口座の銘柄は**判断対象外**。分析しても執行されないため、参考表示にとどめて判断ラベルを付けない。ただし**地合いの判定材料としては使う** (下記)
6. **同一銘柄を複数口座で持つ場合は合算して 1 セクション**にする (現物の市場リスクはティッカー単位で決まる)。口座内訳は補記にとどめ、売却を提案するときだけ税制上の差 (NISA / 特定) に触れる

### STEP 4. 出力フォーマット

**冒頭に STEP 2 で計算した実効保有を置く** (株数がどこから来たかを、読み手が最初に確認できるようにするため)。続いて銘柄ごとに:

```
## 9999 銘柄名 — XXX株 (現値 ¥X,XXX / 前回 MM/DD 比 +X.X%)

前回からの変化: キーレベルに対して価格がどう動いたか (1〜2 行)
シナリオ進捗: [前進 / 停滞 / 否定接近 (無効化 ¥XXX まで -X.X%)]
テクニカル: 週足トレンド🟢 / 日足モメンタム🟡 / 過熱度🔴 / 出来高🟡

判断: ホールド
  - 根拠 2〜3 点
  - トリガー: 「日足終値で ¥XXX を割ったら◯◯」の形で具体レベルを示す
```

**トリガーは必ず確定足ベースで書く** (「日足終値で」)。ザラ場の一時的な上下で判定すると、STEP 1 が確定足で揃えている意味が消える。

最後に総括 (全銘柄に共通するリスク、優先アクション 1 つ)。

### STEP 5. ジャーナルへの記録

**日々の分析はジャーナルに書かない。** 分析の正は中間表現 JSON で、ジャーナルが持つのは
**執行の台帳と運用メモの 2 つだけ** → `docs/adr/0025-journal-as-ledger-and-memo.md`。
**書式は `journal/README.md` に従う** — この SKILL.md に写経しないこと。

書くのは次に当たるときだけ (毎回は発生しない)。

- **売買の報告を受けたら、その場で `### 執行` に記録する。** 分析の実行を待たない。
  この節は**保有の正しさを担保する台帳**で、網羅性がそのまま実効保有の正しさになる
- **訂正** — 過去の分析の誤りが分かったとき。**原因を必ず添える**
- **昇格候補の 1 回目の観測** — 「もう一度起きたら運用ルールへ」の保留状態
- **対話実行での追補と出典** — 外部参照で確定させた事実 (出典 URL つき)
- **規約の例外** — 規約に反する扱いをしたときの記録

追記専用。過去エントリは書き換えない。
**教訓はここに書くだけで終わらせない** — ルールとして固まったものは `journal/lessons.md` に昇格させる (STEP 6)。

### STEP 6. 教訓の昇格

再発防止のルールとして使えるものを `journal/lessons.md` に書き足す。ジャーナルは追記専用で量が増え続けるため、書いた教訓は次回読まれる保証がない。lessons.md は STEP 0 で必ず読まれる場所として用意してある。

**この SKILL.md には書かない。** 教訓は実際の保有についての観測を含み、このファイルは公開リポジトリで追跡されている (→ `docs/adr/0018-bundle-skills-in-repo.md`)。

昇格させる形は「ルール本体」と「経緯」の 2 部構成にする。経緯を落とすと、あとで見直すときに前提が変わったかどうかを判断できない。

## 判断の規範

### データ不足の銘柄に判断ラベルを付けない

- 週足が `{"error": "insufficient"}` を返す、または日足の `ema200` が `null` の銘柄は **判断を「保留」**とし、ホールドを含む他のラベルを付けない
- 併せて「何が足りないか」と「いつ判定可能になるか」を書く (例: EMA200 は 200 営業日必要)

上位トレンドの基準線が無い状態で「ホールド」と書くと、根拠のある継続保有と見分けがつかない。この状態を表現するために「保留」ラベルがある。

### 決算をまたぐ判断

決算注記の読み方 (`⚠` の有無、7 パターン) は `docs/output-contract.md` が正。それを踏まえて:

- **決算が近い場合**: トリガー水準に加えて「決算をまたぐ場合は寄り付きの水準で再判断する」旨を必ず添える。**決算直前の積増しはテクニカルの根拠では正当化できないので提案しない**
- **決算直後の場合**: 直近の日足の大きな変化率を**テクニカルのシグナルとして読まない**。決算反応とトレンド転換は別物で、混同すると一過性のギャップをブレイクと誤認する
- **決算日が不明の場合**: 決算をまたぐ前提でトリガーを書き、直近の値動きが決算反応である可能性も残したまま扱う。**日付を確かめてよいかは実行モードによる** — 可否の正は `docs/output-contract.md` の「実行モードと外部参照」。定期実行では引かず「不明」のまま進む

### 自動運用口座の ETF は地合い判定に使う

- 判断対象外だが、**株式・先進国・新興国・債券・金の ETF が揃っている場合、その並びはリスクオン / リスクオフの判定材料になる**
- 個別銘柄のセクションより先に地合いを固めると、個別の強弱を相対で語れる (地合いが強い中での弱さは、銘柄固有の問題である可能性が高い)

## 注意

- 判断の最終決定はユーザー。積増し・売却を提案するときは、株数ではなくレベルとシナリオを示す
- **「様子見 (ホールド継続)」を恐れない。毎回アクションを提案する必要はない**
- **新規銘柄の発掘はこのスキルの仕事ではない。** 候補探索は `stock-screen` スキル (`screen.py`) の担当。保有分析の途中で母集団の外へ探しに行かない
- **`stock-screen` の 4 ラベル (買い / 見送り / 決算後に再判定 / 保留) とは別体系。**
  あちらは非保有の候補が前提で、同じ中間表現に両方が並ぶ。共通するのは「保留」だけで、
  これは両方とも「データ不足で判定が成立しない」を指す。
  **ラベル定義の正は `docs/report-contract.md`**
  → `docs/adr/0017-screen-report-writes-verdict.md`
- 仮想通貨のスイング分析スキルとは判断ラベルの体系が違う (★なし)。両者のフォーマットを混ぜない
