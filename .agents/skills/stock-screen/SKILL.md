# Stock Screen — 株式候補のスクリーニングと判断

## When to Use

ユーザーが新規の買い候補探し、「候補を探して」「ストックスクリーン」「スクリーニングして」を依頼したとき。対象は **現物の株式・ETF (日本株 / 米国株)**。

- 保有株の分析は `stock-check` の担当。こちらでは扱わない
- 仮想通貨のスイングは別スキルの担当

## 大原則

- **抽出と判断の 2 段構え。** `screen.py` が機械条件で候補を絞り、絞られた候補に `analyze.py` の分析で買いかどうかを判断する。`screen.py` 自体は買い判断をしない — スクリーナーが誤検知しても、コストが「分析 1 回分の工数」で済むようにするための分離 (→ `docs/adr/0006-screener-does-not-decide-buys.md`)。判断ロジックを `screen.py` に足さないこと
- **判断と根拠を明確に書く。** ラベルは `docs/report-contract.md` の候補用定義に従い、根拠が混在する場合は指標ごとの違いを示す。データ不足を断定で埋めず、執行判断はユーザーに委ねる
- **定期実行は質問せず完結する。** 前提とデータ不足を出力に明記し、契約に従って保留・再判定とする。対話実行では、対象や判断を変える未決事項だけ確認する
- **候補ゼロは正常な出力。** 埋め草の候補を作らない。「候補なし」と報告して終えてよい
- **その場で閾値や母集団を緩めない。** 候補が出ないからといって `config/universe.py` の値を触らない。緩めるかどうかはジャーナルに溜まった頻度を見て別途決める
- **確定足だけで判定する。** データ取得は必ず `screen.py` を通す。yfinance を直接叩いたり、他ツールで取った株価を混ぜたりしない
- **このスキルは発注しない。** このリポジトリには発注コードが無く、証券会社の取引 API も追加しない

## 保有・候補情報の扱い

[AGENTS.md の公開リポジトリ規範](../../../AGENTS.md#public-リポジトリ前提の規範)に従う。保有・候補・売買意図は追跡対象外の運用ファイルだけに保存し、Issue・PR・commit へ出さない。

## ファイル構成

パスはリポジトリルートからの相対。**`pip install` は禁止**、常に `uv run` + PEP 723。

- `screen.py` — 機械スクリーニング (STEP 1)
- `analyze.py` — 候補のテクニカル分析 (STEP 4)。`stock-check` と共有
- `docs/output-contract.md` — **出力の読み方の正**。score・通過理由・決算注記・警告の意味、
  および**実行モードごとの外部参照の可否**はすべてここ
- `docs/report-contract.schema.json` — **中間表現の構造の正**
- `docs/report-contract.md` — **中間表現の意味と判断ラベル定義の正**
- `reports/latest.json` — 前回の中間表現 (前回候補の顛末を追う起点)
- `config/watchlist.py` — ウォッチリスト (保有検討中)。追跡対象外。無ければ空リスト扱い
- `config/watchlist.example.py` — その雛形
- `config/universe.py` — 探索ユニバースと閾値 (`MIN_MOVE_IN_ATR` / `MIN_BREAK_IN_ATR` ほか)
- `journal/journal.md` — 執行の台帳 + 運用メモ (追記専用。`stock-check` と共有)
- `journal/README.md` — **執行の書式と、運用メモに何を書くかの正**
- `journal/lessons.md` — 運用教訓 (追跡対象外。無ければ空として扱う)

## 母集団の 3 層

| 層 | 出所 | 扱い |
|---|---|---|
| ウォッチリスト | `config/watchlist.py` | 常に含める。先に取得する |
| 探索ユニバース | `config/universe.py` | 知らない銘柄を拾う枠 |
| 保有 | 保有データ + ジャーナルの `### 執行` | **既定で除外** (`--include-held` で含む) |

保有を除外するのは、既に持っている銘柄が候補に出ても行動が変わらないため。保有側の判断は `analyze.py` と `stock-check` が担う。→ `docs/adr/0010-three-layer-universe.md`

**除外に使うのは実効保有。** 定義と、除外の内訳をどう読むかは `docs/output-contract.md`。

## ワークフロー

### STEP 0. 運用教訓の読み込み

`journal/lessons.md` を読む。過去の運用で判明した注意点が入っている (無ければ初回として扱い、以降のステップをそのまま進める)。

### STEP 1. スクリーニング実行

```bash
uv run screen.py --earnings          # JP + US
uv run screen.py --market jp --earnings
```

`--earnings` は候補にのみ決算日を取得する (候補 1 件につき 1 リクエスト増える)。STEP 3 で使うので既定で付ける。

**出力の読み方は `docs/output-contract.md` に従う。** 実行時刻の条件、確定足が前回と同じ場合の扱い、保有除外の内訳、警告 3 種の意味はすべてそこが正で、この SKILL.md には写経しない。

### STEP 2. 候補の読み取り

出力は score 降順、最大 `MAX_CANDIDATES` 件。**score が ATR 単位であること、通過理由 2 種の意味の違いは `docs/output-contract.md`。**

候補は必ず「何かが起きた」銘柄である (通過条件は状態ではなく事象 → `docs/adr/0011-event-based-screen-thresholds.md`)。

候補ゼロの成立条件と市場別の更新抑止は`docs/report-contract.md`を正とする。夕方ブリーフから
呼ばれた場合は、`screen.py`が返した候補だけを分析する。

### STEP 3. 決算の確認

`--earnings` を付けると候補に決算注記が出る。**日程の報告で終わらせず、トリガーの有効性の問題として扱う** (→ `docs/adr/0009-earnings-date-as-trigger-validity.md`)。注記の 7 パターンと `⚠` の有無による違いは `docs/output-contract.md` を見る。

そのうえで判断に落とすときは:

- **決算が近い (`⚠` 付き)** — 判断は `決算後に再判定`。確定足ベースの水準は決算ギャップで飛び越えられるため、決算前に建てた水準は執行できない可能性がある
- **決算が遠い (`⚠` なし)** — トリガーは有効。決算を理由に判断を先送りしない
- **決算直後 (`⚠` 付き)** — 通過理由が「直近足の動き」なら、**決算反応をブレイクと誤認していないか**を疑う。一過性のギャップとトレンド転換は別物
- **決算日が不明** — **判断は `決算後に再判定` とし、決算日の欄に「不明」と書く**。日付が確定するまで `買い` を確定させない。通過理由が「直近足の動き」なら、決算反応を突破と誤認していないかを疑う (日付が分からない以上、否定もできない)。**日付を調べてよいかは実行モードによる** — 可否の正は `docs/output-contract.md` の「実行モードと外部参照」

### STEP 4. 候補の分析と判断

**候補が 1 件以上あるときだけ** `analyze.py` を回す。候補ゼロなら実行しない (無駄なリクエストになる)。

```bash
uv run analyze.py <候補のティッカーを並べる>
```

候補数の上限は `config/universe.py` の `MAX_CANDIDATES` に従う。

読み方は `stock-check` と同じ **週足 = 上位トレンド、日足 = 執行判断**。分析の結果を 買い / 見送り / 決算後に再判定 / 保留 のどれかに落とす。**ラベル定義の正は `docs/report-contract.md`** の「判断ラベル」にある。信頼度の星は付けない。

`stock-check` の 5 ラベル (ホールド / 積増し / 部分利確 / 売却 / 保留) は保有銘柄用。同じ日付エントリに両方が並ぶので取り違えないこと。

### STEP 5. 出力フォーマット

```
母集団 N 銘柄 (market=all) / 取得失敗 M 件

## 候補 1. 9999 — ¥X,XXX (直近足 +X.X%) [score X.X ATR]
通過理由: 20 日レンジを上に突破 (ATR 0.5 倍)
位置: 20日レンジ ¥XXX〜¥XXX (終値位置 XX%) / ATR X.X% / 売買代金20日平均 ¥XXX
決算: ⚠ 決算 YYYY-MM-DD (あと N 日) — ギャップでトリガーが飛びうる
テクニカル: 週足 [EMA の並び / ADX] / 日足 [RSI・StochRSI・BB %B・OBV]
注目水準: 支持 ¥XXX / 抵抗 ¥XXX

判断: 買い
  - 強い点: 根拠を明確に書く (1〜3 点。数字を添える)
  - 弱い点: 同上。**弱点を書かない「買い」は書かない**
  - 確認点: 「日足終値で ¥XXX を維持できるか」の形で具体レベルを示す
```

**判断は書くが、執行には触れない。** 株数・資金配分・打診買いの是非は書かず、レベルとシナリオを示す (`stock-check` の規定と揃える)。

**確認を求めて止まらない。** 買うかどうかを聞かない。判断と材料を提示して終える。

候補ゼロ、新規スクリーニングなし、取得不能、候補判定なしは`screen.py`の市場別表示を
そのまま使う。意味の正は`docs/report-contract.md`の「市場別表示の意味」。休場か
データ遅延かをこのスキルで推測しない。

### STEP 6. 記録

**夕方ブリーフから呼ばれたときはスクリーニング結果をジャーナルに書かない。** 候補・判断・
所見の正は中間表現 JSON である。一方、単体で起動したときは `reports/latest.json` を更新
しないため、候補・候補ゼロ・判断を `journal/README.md` の「単体分析の記録」に従って残す。

- **候補ゼロの日も記録に残す。** 夕方ブリーフでは中間表現の `candidates: []` と
  `screen.jp` / `screen.us`、単体実行ではジャーナルに残す。候補が出ない日の頻度は、母集団を広げるか
  閾値を緩めるかの判断材料になる
- **前回の候補の顛末を追う。** `reports/latest.json` とジャーナルの単体分析記録のうち、
  より新しい日付を読み、前回「買い」「決算後に再判定」とした候補が今回どうなったか
  (買った / 見送った / 条件が消えた) を当日の `summary` に 1 行で書く
- ジャーナルに書くのは**訂正・昇格候補の 1 回目・対話実行での追補と出典・規約の例外**だけ。書式は `journal/README.md`

### STEP 7. 教訓の昇格

再発防止のルールとして使えるものを `journal/lessons.md` に書き足す。ジャーナルは追記専用で量が増え続けるため、書いた教訓は次回読まれる保証がない。lessons.md は STEP 0 で必ず読まれる場所として用意してある。

**この SKILL.md には書かない。** 教訓は実際の保有・候補についての観測を含み、このファイルは公開リポジトリで追跡されている (→ `docs/adr/0018-bundle-skills-in-repo.md`)。

昇格させる価値があるのは、たとえば次のようなもの:

- 候補の通過理由ごとの当たり外れの傾向
- 「買い」判断の当たり外れの傾向 (外れが続くならラベルの再検討 → ADR-0017 の再評価のサイン)
- 閾値・母集団を変えるべきと判断した根拠と、その結果
- スクリーナーが構造的に拾えない / 拾いすぎるパターン

## 注意

- **判断の最終決定はユーザー。** 「買い」は今の判断材料からの評価であって執行の指示ではない
- **候補ゼロを失敗と扱わない。** 母集団が狭いので出ない日のほうが多い。無理に候補を作るとスクリーナーの意味が消える
- **保有銘柄の分析はこのスキルの仕事ではない。** `stock-check` の担当。スクリーニングの途中で保有の話に流れない
- **判断ラベルの正は `docs/report-contract.md`。** `stock-check` の 5 ラベルとは別体系で、同じ中間表現に両方が並ぶ
- **ファンダの深掘りは別プロジェクト (dexter-jp / 日本株) に回す。** このスキルはテクニカル担当。dexter-jp の LLM 入りツールを機械スクリーニングの代わりに使わない → `docs/adr/0007-split-technical-and-fundamental-research.md`
- 共通の契約を変える場合は `docs/output-contract.md`、`docs/report-contract.md`、`journal/README.md` と呼び出し元への影響を確認する。
