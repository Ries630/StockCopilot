# 出力の読み方（コードとスキルの契約）

`screen.py` / `analyze.py` の出力を**どう読むか**の正はこのファイルにある。
スキル（`stock-check` / `stock-screen`）はここへリンクし、内容を写経しない
（→ [ADR-0018](adr/0018-bundle-skills-in-repo.md)）。

ジャーナルの書式と判断ラベルの定義は対象外。正は
[`journal/README.md`](../journal/README.md) にある。

## 実行時刻と足の鮮度

判定は確定足だけで行う（→ [ADR-0005](adr/0005-completed-bars-only.md)）。
形成中の足を落とす判定は `lib/datasource.py` の `drop_forming_bar()` にあり、
市場ごとの引け時刻は `MARKET_CONFIG` が持つ（JP: 16:00 JST 以降 / US: 16:30 ET 以降）。

- **実行は 16:00 JST 以降。** それより前に回すと JP の当日足がまだ確定していない
- **US 銘柄は JST 実行時に前営業日の足が最新になる。** US の引けが JST 早朝のためで、
  正常な挙動。「US だけデータが古い」と報告しないこと
- **週足は最大 5 営業日古い。** yfinance の週足は月曜始まりで、当週の足は金曜の引けまで
  形成中として落とされる。金曜午前に実行すれば週足は前週末の値になる。週足トレンドを
  語るときは「いつ時点の値か」を意識する（週の途中で日足が大きく動いていても
  週足には反映されていない）

### 確定足の日付が前回と同じとき

市場ごとに`unchanged`とし、**独立した観測として数えない。** 取引日カレンダーを持たないため、
休場かデータ遅延かは断定せず「前回から更新なし」と警告する。

同じ足を別の日の観測として記録すると、シリーズ分析では実在しない値動きを語ることになり、
スクリーニングでは候補ゼロの頻度が水増しされて、母集団や閾値を見直す判断材料が壊れる。

## 保有データの鮮度（`analyze.py`）

保有モードのヘッダに `保有 N 銘柄 / Investment as_of=YYYY-MM-DD (D 日前)` が出る。

**`as_of` が古いことは異常ではない。** Investment の `as_of` はレポート生成では動かず、
証券口座の残高を取り込んだときにだけ更新される。取り込みは高頻度では行わない運用なので、
**古い状態が既定**である。「データが古いので更新してください」と促さないこと
（実行できない指示になる）。

**基準日は資産クラスごとに異なりうる。** 別系統で管理されている資産クラスがある場合、
ヘッダは `as_of は資産クラスで異なる` に変わり、基準日ごとの内訳が続く。
丸めて 1 つの日付として語らない。

**`⚠ 90 日超` が出た場合だけは意味が違う。** これは「データが古い」ではなく
**「執行記録だけで差分を追いきれているか自体が怪しい」**という警告
（閾値は `analyze.py` の `STALE_DAYS`）。執行記録の網羅性に触れたうえで
Investment の同期を提案する。

### 実効保有

保有は `as_of` 時点の保有とジャーナルの執行記録の合成で確定する
（→ [ADR-0015](adr/0015-journal-executions-machine-read.md)）。

```
実効保有 = Investment の as_of 時点の保有 + as_of 以降の執行記録
```

`stock-check` の分析対象も、`screen.py` が母集団から落とす保有も、同じこの定義を使う。
`as_of` が古くても、執行を記録してあれば買った直後の銘柄が候補に出ることはない。

## 決算注記（`lib/earnings.py`）

決算日は**日程を報告するために取るのではなく、確定足ベースのトリガーが有効かを
判断するために取る**（→ [ADR-0009](adr/0009-earnings-date-as-trigger-validity.md)）。
決算はギャップ要因で、「日足終値で X を割ったら」というトリガーを飛び越えて
執行不能にする。`analyze.py` と `screen.py --earnings` が同じ `lib/earnings.py` を
共用する（→ [ADR-0012](adr/0012-shared-earnings-module.md)）。

**`⚠` の有無が判断の分かれ目になる。** `EARNINGS_ALERT_DAYS`（7 日）以内の前後にだけ
`⚠` と但し書きが付き、それより離れていれば日付だけの行になる。

| 出力 | 意味 | 扱い |
|---|---|---|
| `決算 YYYY-MM-DD (あと N 日)` | 8 日以上先 | トリガーは有効。決算前を理由に判断を先送りしない |
| `⚠ 決算 YYYY-MM-DD (あと N 日) — ギャップでトリガーが飛びうる` | 7 日以内 | 確定足ベースの水準は飛び越えられうる |
| `⚠ 決算 YYYY-MM-DD (本日) — ギャップでトリガーが飛びうる` | 当日 | 同上 |
| `⚠ 直近決算 YYYY-MM-DD (N 日前) — 直近の値動きは決算反応の可能性` | 7 日以内 | 直近の大きな変化率をテクニカルのシグナルとして読まない |
| `直近決算 YYYY-MM-DD (N 日前)` | 8 日以上前 | 通常のテクニカルとして読んでよい |
| `⚠ 決算日 不明 (取得できず) — ギャップの可能性を残したままトリガーを書く` | 個別株で取得できず | 下記 |
| 行が出ない | ETF | 決算の概念が無いので正常 |

### 「不明」の読み方

**「決算が無い」ではない**（→ [ADR-0016](adr/0016-surface-unavailable-earnings-date.md)）。
ETF と個別株は `lib/datasource.py` の `fetch_instrument_type()` で切り分けており、
**個別株で行が出ないことは無い**。取れなければ必ず「不明」の行が出る。

- 決算をまたぐ前提でトリガーを書く（寄り付きの水準で再判断する旨を添える）
- 直近の値動きが決算反応である可能性を否定できないので、大きな変化率を
  テクニカルのシグナルとして確定的に読まない
- 日付を確かめてよいかは**実行モードによる**（下記）

## 実行モードと外部参照

**この節が可否の正。** スキルに写経しない。

| モード | 外部参照（Web / IR） | 何が起きるか |
|---|---|---|
| **定期実行**（`stock-brief`） | **引かない** | 取れない決算日は「不明」のまま進む |
| **対話実行**（`stock-check` / `stock-screen` を直接呼ぶ、追加の問い合わせ） | **引いてよい** | 判明したら運用メモに**出典つき**で残す |

### 定期実行で引かない理由

無人で走るため、**外部情報が判断に入る前に人が検証できない**。まとめサイトの日付が
誤っていれば判断が反転し、しかも気づく経路が無い。確定足のみを使う
（[ADR-0005](adr/0005-completed-bars-only.md)）、LLM 入りツールを機械判断に使わない
（[ADR-0007](adr/0007-split-technical-and-fundamental-research.md)）と同じ思想である。

**「不明」は安全側の既定として設計されている**（[ADR-0016](adr/0016-surface-unavailable-earnings-date.md)）。
不明のまま進むと判断は `決算後に再判定` に倒れ、確定足ベースのトリガーは
決算をまたぐ前提で書かれる。**これは劣化ではなく設計どおりの挙動。**

### 対話実行で引いてよい理由

りーすさんが結果を見ており、誤った情報がそのまま判断に残らない。判明した事実は
運用メモに出典つきで残す（書き方は [`journal/README.md`](../journal/README.md)）。

**確定させた情報は「決定的パイプライン外」と明記する。** 株価は必ず
`lib/datasource.py` 経由という境界を崩さないため。

### 恒常的な取得欠損の本筋

yfinance が小型株の決算日を持たないことが原因で、**手動確認リストで埋めない**
（[ADR-0016](adr/0016-surface-unavailable-earnings-date.md) が却下済み）。
決定的な取得経路の整備は
[#20](https://github.com/Ries630/StockCopilot/issues/20)（dexter-jp の TDnet 決算短信）にある。

## スクリーニングの出力（`screen.py`）

### 候補の読み取り

出力は score 降順、最大 `MAX_CANDIDATES` 件（`config/universe.py`）。

- **score は ATR 単位。** 変化率とレンジ突破の両方を ATR に正規化しているので候補間で
  比較できる。生の % ではないので「何 % 動いた」と読み替えない
- **通過理由で意味が違う**
  - `20 日レンジを上/下に突破` — レンジからの離脱。トレンド発生の可能性
  - `直近足の動きが日次 ATR の N 倍` — 単発の大きな動き。ニュース・決算反応でも起きる
- **どちらの条件にも ATR 単位の下限がある**（`MIN_MOVE_IN_ATR` / `MIN_BREAK_IN_ATR`）。
  「レンジの端に近い」は状態であって事象ではないので条件に入っていない。候補は必ず
  「何かが起きた」銘柄である（→ [ADR-0011](adr/0011-event-based-screen-thresholds.md)）

### JSON出力

`--json`では標準出力にJSONだけを出す。母集団、市場、取得失敗数、失敗内容を
`screen.jp` / `screen.us`の`universe` / `evaluated` / `failures` / `matched` / `selected` /
`failure_details`へ入れる。`bars`には、取得できた銘柄から市場ごとの最新確定足日を集約し、
不足市場は探索ユニバースの代表銘柄から補う。それでも取得できなければ日付を推測せず、
その市場のキーを省略して`bar_status`を`unavailable`にする。候補の機械データは
中間表現と同じキー・単位へ決定的に変換する。
特に内部値`range_pos`は比率だが、JSONの`range.pos_pct`は100倍した百分率である。

候補は、全銘柄の走査後に前回の確定足日と比較し、`updated` / `initial`の市場だけへ絞って
からscore順と`MAX_CANDIDATES`を適用する。名前と決算情報は選択後の候補だけ取得する。
`unchanged` / `unavailable`市場は候補分析へ渡さない。

取得例外の警告をJSONの前へ混ぜない。`failure_details`を読み、`failures`件を
「判定できなかった」として報告する。

### 保有除外の内訳

冒頭に次のいずれかが出る（→ [ADR-0010](adr/0010-three-layer-universe.md)）。

```
保有 N 銘柄を母集団から除外 (Investment as_of=YYYY-MM-DD / 執行記録 X 件中 Y 件を適用)
保有 N 銘柄を母集団から除外 (Investment as_of=YYYY-MM-DD / 執行記録なし)
保有除外なし (--include-held)
[warn] 保有データを読めなかったため保有除外なし
```

最後の 1 行が出た回は、**保有銘柄が候補に混じりうる**。

### 警告の 3 種

| 出力 | 意味 | 報告の仕方 |
|---|---|---|
| `[warn] <ticker>: ...` | その銘柄の取得に失敗。**母集団から静かに消えている** | 件数に含めて報告する。「候補なし」と「取得できなかった」は別 |
| `[warn] journal <行番号>: ...` | その行を執行として読めていない | 保有の除外が不完全になりうる。件数と併せて報告する。ジャーナルを直すのはユーザーで、スキルは書き換えない |
| `[warn] 保有データを読めなかったため保有除外なし` | Investment の生成物を読めなかった | 上記のとおり、その回は保有が候補に混じりうる |
