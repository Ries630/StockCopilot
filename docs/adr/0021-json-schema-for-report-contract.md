# ADR-0021: 中間表現の構造をJSON Schemaで検証する

- ステータス: 承認済み
- 日付: 2026-08-21
- 関連: [#61](https://github.com/Ries630/StockCopilot/issues/61) / [PR #64](https://github.com/Ries630/StockCopilot/pull/64)

## 背景

中間表現JSONはLLMが組み立て、HTMLと後続のSlack通知が読む境界である。
最初の実装は`report.py`が使用箇所ごとに必須キーを検証し、その後
`lib/contract.py`へ集約した。

PR #64では5回のレビューで19件の契約違反が指摘された。4回目までの15件を
集約後も、任意の`name`の必須化、空文字の`ticker`、リスト型、必須数値の`null`という
4件が残った。全219テストは0.64秒で成功していたが、実行確認では次の不正入力を受理した。

- `ticker: ""`
- `effective_holdings.lines: "記録なし"`
- `price: null`
- `summary: null`
- `holdings_as_of: "x"`

集約後の実装も、必須キーと一部の語彙をPythonの分岐で列挙しており、型・空・配列要素を
項目ごとに書き忘れられる構造だった。一方、`docs/report-contract.md`の表も同じ構造を
別に記述していたため、文書・実装・テストが同じ漏れを共有できた。

## 決定

キー、型、必須、語彙、配列要素、条件付き必須、未知キーの扱いは
`docs/report-contract.schema.json`（JSON Schema Draft 2020-12）を正にする。
`lib/contract.py`は`jsonschema`でこれを検証し、資金が動く判断と`unknown`の併存など、
業務上の組み合わせだけをPythonで検証する。

`docs/report-contract.md`は構造を写経せず、項目の意味と組み合わせ規則を説明する。

## 検討した代替

**1. 標準ライブラリだけで宣言的な検証表を作る。** 却下。依存は増えないが、
JSON Schemaが既に定義している型、配列、条件分岐、未知キー、エラー位置の処理を
独自実装することになる。今回の問題は独自の部分検証の網羅性だったため、同じ種類の
保守対象を増やさない。

**2. Pydanticモデルを正にしてJSON Schemaを生成する。** 却下。Pythonから使うには
扱いやすいが、正がPythonモデルになり、LLMや将来の別実装が読むJSON境界の仕様としては
生成物を介する。今回は入力JSONそのものの契約を言語非依存のファイルで持つ。

**3. 現行の手書きvalidatorへ指摘された型検証だけを追加する。** 却下。19件を
順番に塞いでも未指摘の`summary: null`などが残ることを実行確認できており、
次の項目追加で同じ漏れを再発できる。

## 結果

`report.py`は標準ライブラリだけでは実行できなくなり、PEP 723の依存へ`jsonschema`が増える。
初回実行時はuvによる依存解決が必要になる。

構造の変更はMarkdownだけでは完結せず、JSON Schemaを先に変更する必要がある。
契約に無い追加キーも拒否するため、互換性を保たず項目を試しに足すことはできなくなる。

## 再評価のサイン

- `jsonschema`の依存解決がスケジュール実行の継続的な障害になったとき
- Python以外の生成側で、Draft 2020-12を利用できないことが判明したとき
- 業務上の組み合わせ検証が増え、JSON SchemaとPythonの境界が判断できなくなったとき
