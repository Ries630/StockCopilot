# ADR-0016: 決算日を取得できなかったことを銘柄種別で切り分けて出力に出す

- ステータス: 承認済み
- 日付: 2026-08-13
- 関連: [#21](https://github.com/Ries630/StockCopilot/issues/21)、[#20](https://github.com/Ries630/StockCopilot/issues/20)、[ADR-0009](0009-earnings-date-as-trigger-validity.md)

## 背景

[ADR-0009](0009-earnings-date-as-trigger-validity.md) で決算日を取得すると決めた時点で、
その「結果」節に限界を記録していた。**行が出ないとき、ETF で決算の概念が無いのか、
個別株で取得できなかったのかを出力上区別できない**、というもの。

2026-08-10 の保有分析でこれが実害になった。保有小型株 1 銘柄について「決算日を
取得できなかった（不明）」とジャーナルに記録したが、実際には**その 3 営業日前の場中に
四半期決算を開示済み**だった。決算反応による日足の上昇をテクニカルの進捗として読み、
短期過熱の指標も決算反応が作った数字と気付かないまま記録した。後から Web 検索で
決算日が判明し、ジャーナルに訂正を追記している。

`stock-check` / `stock-screen` の SKILL.md には既に「個別株で行が出ないのは
『決算が無い』ではなく『取得できなかった』」という解釈ルールがある。
**漏れたのはルールの不在ではなく、ルールを適用する起点が出力に無いこと。**

コード上、`None` に潰れる経路は 2 つある（`lib/datasource.py` の `fetch_next_earnings()`）。

- ETF は fundamentals を持たず calendar が 404 になり、例外経路で `None`
- 個別株でも yfinance がデータを持たない場合があり、`Earnings Date` が空リストで `None`

判断の前提として、2026-08-13 に yfinance の挙動を測った（`uv run` の使い捨てスクリプト）。
**以下のティッカーは挙動を確かめるために選んだ例であり、保有とは関係しない**
（[ADR-0008](0008-no-holdings-in-repo.md)）。

| ティッカー | `calendar` の `Earnings Date` | `history_metadata["instrumentType"]` |
|---|---|---|
| VTI（ETF） | `None`（404） | `ETF` |
| 1306.T（ETF） | `None`（404） | `ETF` |
| AAPL | `[date(2026, 10, 30)]` | `EQUITY` |
| 7203.T | `[date(2026, 11, 5)]` | `EQUITY` |
| 3350.T（小型株） | `[]`（空） | `EQUITY` |

`instrumentType` は ETF と個別株を明示的に切り分けた。`fast_info.quote_type` も同じ値を
返したが、出どころは同じ price チャートのメタデータ。取得は 1 リクエストで、
呼ぶのは決算日が取れなかった銘柄だけに絞れる（対象は保有銘柄と候補のみで、現状は数銘柄）。

## 決定

「決算日が取れない」を銘柄種別で切り分け、**個別株なら「不明（取得できず）」を 1 行として
出力に出す**。ETF は従来どおり何も出さない（決算の概念が無く、出ないのが正常）。

- 種別の取得は `lib/datasource.py` の `fetch_instrument_type()` に置き、
  yfinance の語彙を `"etf"` / `"equity"` に正規化する。データ源の語彙は
  ここより上に漏らさない（[ADR-0004](0004-yfinance-as-data-source.md) の方針）
- 「個別株 + 日付なし = 不明」という解釈と文言は `lib/earnings.py` に置く
  （[ADR-0012](0012-shared-earnings-module.md) のとおり、注記の正は 1 箇所）
- 呼ぶのは日付が取れなかったときだけ。日付が取れた銘柄でリクエストを増やさない
- **種別の判定自体に失敗した場合も「不明」として出す。** ETF と確定できていない以上、
  警告を出す側に倒す

## 検討した代替

- **`calendar` の形で切り分ける（404 なら ETF、空リストなら取得欠損）** — 追加リクエストが
  0 で済む。落としたのは、yfinance のエラー挙動という**明示されていない性質に依存する**ため。
  一時的な 404 と ETF が区別できず、外れたときに「決算が無い」側（実害のある方向）へ静かに倒れる
- **`fetch_next_earnings()` の戻り値を日付＋状態の複合型にする** — 呼び出しは 1 回で済むが、
  日付と種別という独立した 2 つの事実が 1 つの戻り値に同居し、データ源を差し替えるたびに
  分類まで実装が要る。既存の戻り型 `dt.date | None` に依存したテストと README の記述にも波及する
- **取得できない銘柄を `config/` の「手動確認リスト」に持つ**（#21 の 3 番目の案） — 中身は
  保有か検討中の小型株の集合になり、[ADR-0008](0008-no-holdings-in-repo.md)（保有と売買意図を
  リポジトリに残さない）と正面から当たる。可視化すれば「気付けない」という実害自体は消えるため、
  今は作らない。恒常的な取得欠損の本筋の解決は
  [#20](https://github.com/Ries630/StockCopilot/issues/20)（dexter-jp の TDnet 決算短信）側にある
- **種別を判定せず、日付が取れなければ常に「不明」を出す** — 実装は最も簡単だが、
  ETF に毎回「不明」が出る。決算の概念が無い銘柄への警告は情報を持たず、
  警告全体の重みを下げる
- **対処せず、スキルの解釈ルールに委ねる** — 現にそれで漏れた。ルールはあったが、
  「不明」という状態が出力に現れないため、適用すべき場面かどうかが読み手に分からない

## 結果

- **決算日が取れない銘柄では 1 リクエスト増える。** ETF を保有している限り、
  保有分析のたびに ETF の本数ぶん増える
- **yfinance の `instrumentType` に新しく依存する。** [ADR-0004](0004-yfinance-as-data-source.md) は
  差し替え点を `fetch_ohlcv()` / `fetch_next_earnings()` の 2 関数と定めていたが、
  移植対象が 3 関数になった
- **ネットワークが不安定なときは ETF にも「不明」が出る。** 誤りは安全側に倒れるが、
  警告の信頼度はその分下がる
- **「行が出ない」の意味が変わる。** これ以降は「ETF なので正常」だけを指す。
  `stock-check` / `stock-screen` の SKILL.md にある解釈ルールを更新する必要があり、
  **これらはリポジトリ外のファイルなので CI では守られない**
- **決算日そのものは埋まらない。** システムは毎回「不明」と言うだけで、
  実際の決算日を調べるのは人の作業のまま残る

## 再評価のサイン

- [#20](https://github.com/Ries630/StockCopilot/issues/20) で dexter-jp の TDnet 決算短信を
  非対話で呼べるようになったら、個別株のフォールバック取得先として使える。
  そのとき「不明」は取得の失敗ではなく、最後の手段まで失敗したことを指すようになる
- 「不明」が定常的に多数出るようになったら（探索ユニバースに小型株が増えたら）、
  手動確認リストを見送った判断を再検討する
- yfinance が `instrumentType` を返さなくなる、または ETF でも calendar を返すようになったら、
  切り分けの前提が崩れる
