# ADR-0018: スキル定義を汎用化してリポジトリに同封し、個人の運用教訓は追跡対象外に分離する

- ステータス: 承認済み
- 日付: 2026-08-14
- 関連: [#46](https://github.com/Ries630/StockCopilot/issues/46)、[#47](https://github.com/Ries630/StockCopilot/issues/47)、[#48](https://github.com/Ries630/StockCopilot/issues/48)、[ADR-0008](0008-no-holdings-in-repo.md)

## 背景

`stock-check` / `stock-screen` の SKILL.md は `~/.claude/skills/` にあり、リポジトリの外に
置かれている。README には「スキル定義そのものはリポジトリ外」と書いてあるが、これは
判断を記録した文ではない。テスト・CI・README を整備したコミット（`564ad38`）で、
既にそうなっている状態の説明として入ったもので、ADR も無い。Claude Code の既定の
置き場所をそのまま使った結果である。

この配置で 2 つの問題が起きていた。

**スキルの変更履歴がどこにも残らない。** `~/.claude` はバージョン管理下にない
（`git -C ~/.claude rev-parse` が `not a git repository`）。両 SKILL.md は合計 356 行あり、
判断ラベルの定義も、ジャーナルから昇格した運用ルールも、その経緯も全部そこにある。

**コードとスキルの契約が二重管理になっている。** CLAUDE.md の単一情報源規範に反する
写経が実在した。決算注記 4 パターンの読み方（stock-check:154-157 / stock-screen:94-97）、
実行時刻 16:00 JST と US 足の見え方（:65 / :70）、確定足の日付が前回と同じ場合の扱い
（:67 / :72）が、2 つの SKILL.md に重複して書かれていた。ADR-0017 が
「`stock-screen` スキルの運用規範を作る過程で、この決定を…」と書いている通り、
コード側の決定とスキル側の規範は同じ判断から生まれることが実際にあり、
片方を変えたときもう片方が古くなる関係にある。

同封を検討するにあたり、公開リポジトリの規範（[ADR-0008](0008-no-holdings-in-repo.md)）
との関係を確認した。ADR-0008 が守るのは銘柄名の秘匿ではなく「資産と売買意図を
リポジトリに残さない」ことである。SKILL.md には保有についての観測が経緯として
書かれているが、**同じ性質の記述は既にリポジトリにコミットされている**。
ADR-0016 の背景節にある「保有小型株 1 銘柄について『決算日を取得できなかった（不明）』と
ジャーナルに記録したが、実際にはその 3 営業日前の場中に四半期決算を開示済みだった」が
それで、SKILL.md:161 の経緯とほぼ同文である。銘柄名を伏せた保有エピソードを判断の
根拠として残すことは、ADR-0008 の下で既に容認された運用だった。

個人依存の実態も確認した。Investment への依存は `lib/holdings.py` が
`report_data_*.json` の `stock.holdings` を読むだけで、SKILL.md 側は `as_of` の意味を
説明しているにすぎない。汎用化の障害にはならない。自動運用口座（ロボアド）の扱いと
複数口座・NISA/特定の税制の差は Investment とは別の依存だが、日本の個人投資家一般の
話でもある。

## 決定

スキルを汎用化して `.claude/skills/` に同封する。あわせて次の 2 つを行う。

- `screen.py` / `analyze.py` の出力をどう読むかの正を `docs/` の 1 ファイルに集約し、
  両スキルからリンクする（判断ラベルの定義は `journal/README.md` が既に正なので動かさない）
- 「運用ルール（ジャーナルの教訓から昇格したもの）」は追跡対象外の `journal/lessons.md` に
  分離する。SKILL.md には昇格ループの記述だけを残し、内容は書かない

## 検討した代替

**現状維持 + `~/.claude` を private リポジトリ化する。** 履歴の問題はこれで解決し、
ADR-0008 との衝突も起きない。りーすさんが別リポジトリを増やしたくないという理由で
不採用にした。加えて、この案では契約の二重管理が残る。

**教訓も匿名化してリポジトリに同封する。** ADR-0016 の前例があるので単発なら問題ない。
落とした理由は蓄積の速度である。運用のたびに保有についての観測が 1 つずつ公開
リポジトリに積まれる形になり、しかも「上場後 38 営業日の銘柄」（stock-check:150）の
ような記述は日付と組み合わせると候補がかなり絞れる。ADR は判断のたびにしか書かないので
頻度が低く、そこが前例との差になる。

**教訓を ADR に寄せる。** 履歴も理由も最も強く残る。落としたのは、コード変更を
伴わない運用だけの教訓が行き場を失うため。「候補ゼロの日の頻度」「通過理由ごとの
当たり外れの傾向」（stock-screen:164-169 が昇格候補として挙げているもの）は
ADR の粒度に合わない。

## 結果

**教訓の履歴が残らない。** `journal/lessons.md` は追跡対象外なので、いつ何を昇格させたかを
後から追えず、バックアップも無い。ADR-0017 の再評価のサイン（「買い」の外れが続いたら
ラベルを再検討する）は lessons.md の蓄積を見て判断することになるが、その蓄積自体が
失われうる。りーすさんはスキルの履歴問題を優先度低めと判断しており、この代償を
承知のうえで選んでいる。

**スキルの運用ルールを PR でレビューできない。** 同封したことでワークフローや契約は
PR に載るようになるが、教訓は載らない。ジャーナルと同じく、書きっぱなしを検出する
仕組みが無い。

**SKILL.md に個人の事情を書けなくなる。** スキルを自分向けに調整したくなったとき、
汎用部分と lessons.md のどちらに書くかを毎回判断する必要がある。この線引きを
誤ると、公開部分に個人の事情が混ざるか、汎用の規範が lessons.md に埋もれる。

**`~/.claude/skills/` の他スキルとは配置が非対称になる。** `swing-check` などは
引き続きリポジトリ外にあり、スキルの置き場所が 2 系統になる。

**スキルがリポジトリの外から起動できなくなる。** `~/.claude/skills/` のスキルは
どのディレクトリからでも起動するが、`.claude/skills/` のスキルはそのリポジトリを
作業ディレクトリにしているときだけ読み込まれる。「保有株を分析して」を任意の場所から
呼ぶ運用と、スケジュール実行の設定は、作業ディレクトリを StockCopilot に固定する
必要がある。両スキルとも `uv run` を StockCopilot 配下で実行する前提なので実害は
小さいと判断したが、起動の間口が狭くなること自体は代償である。

## 再評価のサイン

- `journal/lessons.md` を失った、または参照されないまま形骸化した
  → 分離が機能していない。同封か ADR 化に寄せ直す
- 汎用スキルに書けない調整が lessons.md に積み上がり、SKILL.md 本体と
  食い違い始めた → 同封の前提（大部分が汎用である）が崩れている
- `docs/` に切り出した契約とスキルの記述が再びずれた
  → 切り出す境界を引き直す
