# ADR-0025: ジャーナルの役割を「執行台帳 + 運用メモ」に絞る

- ステータス: 承認済み
- 日付: 2026-08-21
- 関連: [#60](https://github.com/Ries630/StockCopilot/issues/60) / [#69](https://github.com/Ries630/StockCopilot/issues/69) / [ADR-0020](0020-intermediate-report-json.md)

## 背景

[ADR-0020](0020-intermediate-report-json.md) で中間表現 JSON を挟んだ結果、同じ分析が
ジャーナルと JSON に二重に書かれる状態になった。あの ADR の「結果」節では代償として
記録したうえで、**「ジャーナルが人間向けの正、JSON が機械向けの正」**という役割分担で
処理するとした。

2026-08-21 にりーすさんから「JSON の新設によってジャーナルの用途は何になるのか。
単一情報源の原則に反する」と指摘を受け、あわせて**ジャーナルを一度も読んでいない**ことが
分かった。**人間向けの正は、読まれて初めて成立する。** ADR-0020 のあの一文は前提が
誤っており、原則違反を役割分担と言い換えて先送りしていた。

### 測定 (2026-08-21)

`journal/journal.md` は 3,405 行 / 12 エントリ (2026-08-06〜08-20)。見出しで分類すると:

| 分類 | 行数 | 割合 |
|---|---|---|
| 定型の分析 (JSON で代替可) | 2,788 | 81.9% |
| 例外・訂正・外部参照 | 315 | 9.3% |
| その他 | 174 | 5.1% |
| 執行 | 128 | 3.8% |

機械が読むのは `### 執行` だけで、`lib/journal.py` は約定日 / 銘柄 / 残株数の 3 項目しか
パースしない ([ADR-0015](0015-journal-executions-machine-read.md))。

兄弟プロジェクトの `swing/journal.md` は 194 行 / 11 エントリ (6 週間) で 1 エントリ 17 行。
StockCopilot は 1 エントリ 283 行で、密度が 16 倍違う。より本質的な違いとして、
**TradingCopilot の日次自動経路 (morning brief) はジャーナルを書かない。**
`swing/journal.md` を書くのは on-demand の `swing-check` だけである。

### 9.3% の中身

「例外・訂正・外部参照」は JSON に居場所が無く、かつ価値が高かった。

- **訂正 (5 件)** — 過去エントリの誤りと**その原因**。うち 1 件
  (「`git fetch` していなかったためローカル `main` が 7 コミット遅れ、実装済みの機能を
  不備と誤認した」) は、りーすさんの個人指示の Git 規約に昇格している
- **昇格候補の「1 回目の観測」(3 件)** — 「同種の事象がもう一度起きたら運用ルールへ
  昇格させる (今回は記録のみ)」。`lessons.md` は昇格**後**の置き場なので、
  1 回目の置き場が消えると 2 回目が来ても昇格を判断できない
- **対話実行での追補と出典** — 定期実行で「不明」としたものを対話で確定させた記録。
  URL 一覧と「決定的パイプライン外」という但し書きがある
- **規約の例外** — 「過去エントリは書き換えない規約だが、当日訂正として明示の判断で
  書き換えた」および「Slack には旧表現が残り、この投稿とエントリは食い違う」
- **指標の読み方を覆す一次観測** — ストップ高で引けた日の score を
  「動いた」ではなく「動いた時点で止められた」と読む、という記録

## 決定

ジャーナルの役割を 2 つに絞る。

1. **執行の台帳** — `lib/journal.py` が読む。実効保有の正 ([ADR-0015](0015-journal-executions-machine-read.md))
2. **運用メモ** — 訂正 / 昇格候補の 1 回目の観測 / 対話実行での追補と出典 / 規約の例外

**定型の分析 (保有分析・スクリーニング・実効保有の提示・前提・Slack 投稿結果) は書かない。**
それらは `reports/YYYY-MM-DD_evening.json` が正で、人が読むのは HTML レポートになる。

これで単一情報源が回復する。「毎日必ず出るもの」は JSON、「その日限りの例外」は
ジャーナルで、両者は重複しない。

あわせて、**判断ラベルの定義の正を `journal/README.md` から
[`docs/report-contract.md`](../report-contract.md) へ移す。** ジャーナルが分析を扱わなく
なる以上、その書式仕様がラベルを所有し続けるのは筋が通らない。

## 検討した代替

**1. 執行の台帳だけに絞る。** 却下。当初はこちらを推奨したが、精査の結果 9.3% を
失うことが分かった。とくに「昇格候補の 1 回目の観測」は `lessons.md` にも JSON にも
居場所が無く、消えると再発時に昇格を判断できなくなる。

**2. 銘柄固有の継続メモ (`### 銘柄メモ`) を置く。** 却下。
[ADR-0016](0016-surface-unavailable-earnings-date.md) が「取得できない銘柄を
`config/` の手動確認リストに持つ」案を**既に却下している**。追跡対象外のジャーナルに
置けば [ADR-0008](0008-no-holdings-in-repo.md) の CI 検査は回避できるが、ADR-0016 の
反対理由は検査ではなく解決の形そのものだった。恒常的な取得欠損の本筋は
[#20](https://github.com/Ries630/StockCopilot/issues/20) にある。

**3. JSON からジャーナルを生成する。** 却下。生成物になるため「一度書いた記録を
書き換えない」規約と衝突する。手書きの執行記録と生成部分が同じファイルに混ざるのも
壊れやすい。

**4. 現状維持 (両方に書く)。** 却下。実装コストは 0 だが、読まれない記録が
月 2,000 行規模で積み上がり続け、JSON との食い違いのリスクも残る。

## 結果

**分析の履歴が `reports/` の日付別ファイルに移る。** ディレクトリごと消すと過去が
すべて消える。これまでは 1 ファイルだったのでバックアップが簡単だった。

**過去 3,405 行は残るが、書式が途中で変わる。** 追記専用の規約により過去は
書き換えないため、2026-08-20 までは定型分析を含み、以降は含まない。読む側は
どこで変わったかを知っている必要がある。

**「前回との差分」の起点が `reports/latest.json` に移る。** 切り替え当日はまだ
JSON が 1 件も無いため、ジャーナルの最終エントリを読む fallback をスキルに残す。
これは移行期のみ必要な経路で、消し忘れると原則が曖昧なまま残る。

**判断ラベルの定義の参照点が動く。** `journal/README.md` を正としていた
[ADR-0017](0017-screen-report-writes-verdict.md) の記述と、スキル 3 本のリンクが
`docs/report-contract.md` を指すようになる。

## 再評価のサイン

- 運用メモに書くことが毎日発生するようになったら、それは例外ではなく定型なので
  中間表現の項目に足す
- `reports/` を消して困ったことが起きたら、バックアップの経路を用意する
- 移行が済んで JSON が溜まったら、スキルからジャーナル fallback を消す
