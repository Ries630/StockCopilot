# ADR-0031: analyze.py の保有モードも実効保有で動かし、株数を決定的に出す

- ステータス: 承認済み
- 日付: 2026-11-17
- 関連: Issue #55 / Issue #37 / ADR-0015

## 背景

ADR-0015で、`screen.py` の母集団除外はジャーナルの執行記録を機械で読み、Investment の
`as_of` 時点の保有と合成した実効保有を使うようにした。一方 `analyze.py` の保有モードは
`as_of` 時点のスナップショットをそのまま読んでいた。

`as_of` は証券口座の残高を取り込んだときにしか動かないので、乖離は通常運用で常に起こる。
夕方ブリーフの試運転では、日本株の保有モードが 3 か月前の一覧のまま読まれ、売却済みの
2 銘柄が分析対象に残り、購入済みの 3 銘柄が抜けていた。定期実行は毎回、LLM が
ジャーナルを読んで実効保有を組み直す回避策で動いていた。同じ「実効保有」が決定的コードと
LLM の読み取りの 2 経路で作られ、食い違ったときにどちらが正かの決めもなかった（#37）。

## 決定

`lib/holdings.py` の公開 API を `effective_holdings()` 1 つにし、`screen.py` の除外と
`analyze.py` の保有モードの両方がこれを使う。戻り値は実効保有の行の一覧と、合成の内訳
（基準日・読めた執行の件数・反映した件数・解釈できなかった行の警告）を持つ。

株数は執行記録の残株数をそのまま使い、パーサが読む項目（約定日 / 銘柄 / 残株数）は
増やさない。執行を反映した銘柄は Investment の行から銘柄名・口座・資産クラスを引き継ぎ、
Investment に行が無い新規の銘柄は、市場をティッカーから推定し、銘柄名は辞書と
yfinance から引き、口座は「口座不明」と表示する。

`analyze.py` は保有モードの冒頭に組み立て（基準日 + 執行記録の件数）を出し、`stock-check`
はそれを実効保有の正として使う。売買別・単価などの執行の内容は、引き続き LLM が
ジャーナルから拾って提示に添える（#37 の案 B）。

## 検討した代替

- **`load_holdings()` 自体を実効保有にする（#55 の案 a）。** 呼び出し側は変わらないが、
  `held_tickers()` と合成ロジックが 2 つ残る。合成を 1 か所にするため、関数ごと置き換えた。
- **件数の差だけを警告する（#55 の案 c）。** 抜けること自体が直らず、LLM の回避策も残るため
  不採用。
- **パーサに売買別・株数・単価を足し、執行の内容まで決定的に出す（#37 の案 A）。**
  ADR-0015 が避けた「読む項目が増えるほど書式ゆれで壊れる」方向に進む。保有モードが
  要るのは残株数で、執行の内容は人が誤りに気付くための提示なので、LLM の読み取りで足りる。

## 受け入れた代償

- 残株数は銘柄単位の合計なので、執行を反映した銘柄は口座をまたいで 1 行にまとまる。
  口座ごとの株数はジャーナルから分からない。NISA と特定口座の区別が売却判断に効く場合は、
  ジャーナルの執行の内容から読む。
- 新規に買った銘柄の口座は、Investment の `as_of` が次に動くまで「口座不明」のままになる。

## 再評価の条件

- 口座ごとの株数を機械で扱う必要が出たとき（ジャーナルの書式に口座を必須項目として足すか、
  Investment の更新頻度を上げるかを比べる）。
