# 分析ジャーナルの仕様

保有分析 (`stock-check`) の継続記録である `journal/journal.md` の書式と運用ルール。

## journal.md は git 追跡対象外

**`journal/journal.md` は `.gitignore` で除外している。** 中身が保有銘柄・株数・口座名・
売買判断の時系列＝個人の資産情報になるためで、このリポジトリが public であることが前提。
ジャーナル本体をコミットしてはならない。ここ (README.md) には書式だけを置く。

存在しない場合は `stock-check` が下記の書式で新規作成する。

## 書式

書式は TradingCopilot `swing/journal.md` に倣う。

- 1 回の分析 = 1 エントリ。見出しは `## YYYY-MM-DD`
- 保有分析 (`stock-check`) とスクリーニング (`stock-screen`) は**同じ日付エントリに同居**させる。
  別ファイルに分けると、候補に挙げた銘柄をその後買ったかどうかの突合が手作業になる
- 銘柄ごとにシナリオ・主要水準・判断 (ホールド/積増し/利確) を残す
- 次回の分析は前回エントリとの突合から始める
- 過去エントリは書き換えない。訂正は新しいエントリに理由付きで書く
- 運用ルールとして固まった教訓は SKILL.md へ昇格させ、ここには経緯を残す

### エントリのテンプレート

```markdown
## YYYY-MM-DD (Investment as_of=YYYY-MM-DD)

- **9999** 銘柄名 | 現値 ¥X,XXX (前回比 +X.X%) | 判断: ホールド
  - キーレベル: 支持 ¥XXX / 抵抗 ¥XXX / 無効化 ¥XXX
  - シナリオ進捗: 前回シナリオが 前進 / 停滞 / 否定接近 のどれか (1 行)
  - トリガー: 日足終値で ¥XXX を割ったら◯◯
- **AAPL** 銘柄名 | 現値 $XXX (前回比 +X.X%) | 判断: 部分利確
  - (同上)
- 総括: 全体に共通するリスクと、優先アクション 1 つ (1〜2 行)

### スクリーニング (母集団 N 銘柄 / market=all)

- **9999** | ¥X,XXX | score X.X ATR | 20 日レンジを上に突破 (ATR 0.5 倍)
  - テクニカル: 週足 [EMA の並び / ADX] / 日足 [RSI・StochRSI・BB %B・OBV]
  - 注目水準: 支持 ¥XXX / 抵抗 ¥XXX
  - 次アクション: 判断へ / 見送り (理由) / 決算後に再判定 (決算 YYYY-MM-DD)

### 執行

- YYYY-MM-DD | **9999** 銘柄名 | 売却 100株 @ ¥X,XXX | 約定代金 ¥XXX,XXX | **残 200株**
```

補足:

- **判断ラベルは ホールド / 積増し / 部分利確 / 売却 / 保留 の 5 種**に限る。信頼度の星は付けない
  (現物のホールド判断は perp より単純で、毎回付けると形骸化するため。swing-check とは異なる)。
  **「保留」はデータ不足で判定が成立しない場合のみ** — 上場後日が浅く週足や EMA200 が
  算出できない銘柄がこれにあたる。根拠なく「ホールド」と書くと継続保有の判断と区別できなくなる
- **決算が近い / 直近にあった銘柄はその旨を書く。** 決算はギャップ要因で、確定足ベースの
  トリガーを飛び越えて執行不能にする。日程の記録ではなくトリガーの有効性の問題として扱う
- 見出しに保有データの `as_of` を併記する。分析日と保有の基準日がずれるため、
  これが無いと後から「増減を見落としたのか、データが古かったのか」を切り分けられない
- 自動運用口座 (ロボアド等) の銘柄は判断対象外。書く場合は参考として明示する
- **トリガーは確定足ベースで書く** (「日足終値で」)。ザラ場の一時的な上下では判定しない

## スクリーニングの記録

`stock-screen` が出した候補を、同じ日付エントリの `### スクリーニング` に残す。
目的は**事後に候補の精度を追えるようにすること**で、記録が無いと
「閾値が緩かったのか、母集団が悪かったのか、地合いだったのか」を後から切り分けられない。

- **候補ゼロの日も 1 行残す** (`- 候補なし`)。候補が出ない日の頻度そのものが、
  母集団を広げるか閾値を緩めるかを判断する材料になる。記録しないとこの頻度が失われる
- **確定足が前回と同じ日は、その旨を書き「独立した観測として数えない」と明記する。**
  土日・祝日・連休をまたぐと同じ足で 2 回実行される。これを別々の観測として数えると
  候補ゼロの頻度が水増しされ、上の判断材料そのものが壊れる
- **見出しに母集団の件数と `--market` を書く。** 母集団や閾値を変えたあとに
  候補数を比較できるようにするため。数だけ見ても、母集団が変わっていれば意味が違う
- **候補にはテクニカルと注目水準を残す。** 候補が出た時点で `analyze.py` まで回すため、
  判断材料はその場で揃う。後から「なぜ見送ったか」を検証するには、見送った当時に
  見えていた指標値が要る (後で取り直すと、その時点の値は復元できない)
- **候補には必ず次アクションを書く。** 見送るなら理由を 1 行添える
  (後から「なぜ見送ったか」を追えないと、見送りの判断自体を検証できない)
- **候補の行に「買い」の判断を書かない。** 分析まで進めても、書いてよいのは
  「何が起きたか」と「どの水準が意味を持つか」まで。買う / 買わないの結論は書かない。
  買った場合は、以降の追跡が保有分析側のエントリに移る
- **前回の候補の顛末を追う。** 前回「判断へ」とした候補が今回どうなったかを
  1 行で書く (買った / 見送った / 条件が消えた)。追わないと候補が出しっぱなしになる

## 執行の記録

売買を `### 執行` に残す。`### スクリーニング` と同じ階層で、同じ日付エントリに置く。

これは記録のためだけの節ではなく、**保有の正しさを担保する台帳**である。保有データの出所
(Investment) の `as_of` はレポート生成では動かず、証券口座の残高を取り込んだときにだけ更新される。
その取り込みは高頻度では行わないため、`as_of` が古い状態が既定になる。そこで保有を次のように定める。

```
実効保有 = Investment の as_of 時点の保有 + ジャーナルに記録した以降の執行
```

`as_of` の鮮度に依存しなくなる代わりに、**この節の網羅性が保有の正しさそのもの**になる。

- **売買した時点で記録する。** 分析を実行するときにまとめて思い出す形にしない。
  約定直後が単価・株数ともに最も正確で、後から思い出すと精度が落ちる
- **1 件につき書くもの**: 約定日 / 銘柄 / 売買別 / 株数 / 単価 / 約定代金 / **執行後の残株数**
- **残株数を必ず書く。** 差分 (「-100株」) だけを積み上げる形にすると、1 件の記録漏れが
  以降すべての残高を狂わせ、しかも狂ったことに気づけない。残株数があれば、その行だけで
  残高が確定する
- 口座区分に触れるのは**税制上の差が判断に効く場合のみ** (NISA での売却など)。
  保有分析エントリの規定と揃える
- **Investment の更新は「同期ポイント」として使う。** `as_of` が動いたときに、
  新しい保有と「古い `as_of` + 執行記録」を突合すれば、記録漏れをそこで検出できる。
  低頻度の更新が監査の役割を果たす
